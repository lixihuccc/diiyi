## 一、背景与现状分析

### 1.1 一句话结论

平台已经具备**"谁能拥有什么角色、角色拥有什么权限"的数据和操作界面**，但完全没有**"请求发生时怎么校验权限"**的能力。V2 要把这套数据变成真正的访问控制，并补上数据级隔离。

### 1.2 现状核查（基于代码）

| 能力 | 现状 | 证据 |
|---|---|---|
| 用户-角色-权限数据模型 | ✅ 已具备三表 + 两张关联表 | `users`、`roles`、`permissions`、`user_roles`、`role_permissions` |
| 角色/权限/用户 CRUD | ✅ 已实现 | `src/modules/{user,role,permission}/api.py` |
| 分配角色、分配权限接口 | ✅ 已实现 | `PUT /users/{id}/roles`、`PUT /roles/{id}/permissions` |
| 登录认证（JWT） | ✅ 已实现，30 分钟有效期 | `src/modules/auth/service.py` |
| 登录校验覆盖范围 | ⚠️ 仅 `GET /users/me` 和知识库上传接口挂了 `get_current_user` | 其余接口无需登录即可访问 |
| 接口级权限校验 | ❌ 完全没有 | 全仓库无权限校验依赖或中间件 |
| 前端登录态守卫 | ✅ 仅判断 token 是否存在 | `app/src/components/AuthGuard.tsx` |
| 前端菜单/按钮权限控制 | ❌ 完全没有 | `DashboardLayout.tsx` 菜单为静态列表 |
| 当前用户返回权限信息 | ❌ 不含角色和权限 | `GET /users/me` 返回 `UserRead`（id/username/email/is_active） |
| 数据归属字段 | ⚠️ 有 `created_by` 字符串（姓名），不可用于鉴权 | `agents`、`knowledge_bases`、`prompts`、`tools` |
| 数据可见范围字段 | ❌ 没有 | 四张业务表均无 `visibility` |
| 角色数据范围 | ❌ 没有 | `roles` 表无 `data_scope` |
| 授权变更审计 | ❌ 没有 | 前端有页面，后端无实现 |

### 1.3 由此产生的实际问题

1. **任何人都能调用管理接口**：`POST /roles`、`DELETE /users/{id}`、`DELETE /agents/{id}` 当前不校验登录，拿到地址即可操作。
2. **权限数据只是"摆设"**：即使把用户配成只读角色，后端也不会拦截任何请求。
3. **前端会误导用户**：所有菜单对所有人可见，点击后才可能失败，且失败原因不明确。
4. **无法做数据隔离**：运营人员能看到并修改全公司所有 Agent、知识库，无法支撑真实的企业分权使用。
5. **越权不可追溯**：谁给谁授了权、什么时候授的，系统里没有记录。

### 1.4 本次目标（Goals）

- **G1**：所有业务接口默认要求登录，并按"功能权限"校验，未授权返回明确错误。
- **G2**：建立可维护的权限码体系，覆盖平台全部现有接口，并支持模块级通配授权。
- **G3**：前端按权限控制菜单、路由、按钮，未授权入口不可见/不可达。
- **G4**：业务资源（Agent、知识库、Prompt、工具）具备归属人和可见范围，列表与详情按数据权限过滤。
- **G5**：授权关系（角色-权限、用户-角色）变更后，权限在可接受时间内生效，且不允许越权授权。
- **G6**：权限模型可扩展，后续新增业务模块只需登记权限码，不改造校验框架。

### 1.5 非目标（Non-Goals）

- 不做部门/组织架构（无部门表、无用户部门归属、无树形层级）。
- 不做 ABAC / 属性级动态策略、字段级脱敏、行级 SQL 策略引擎。
- 不做多租户隔离（同一部署内只有一个组织）。
- 不做 SSO / OAuth2 / 企业微信 / LDAP 登录。
- 不做审批流（申请-审批-授予）。
- 不做 API Key 的权限体系（前端有页面，后端未实现，V2 只保留权限码位）。
- 不做登录风控、限流、密码策略强化。

### 1.6 反目标（Anti-Goals，技术上做成了也算失败）

- **不能只在前端隐藏**：绕过前端直接调接口必须被拒绝。
- **不能让每个业务方法自己写过滤条件**：数据权限必须在统一入口收口，否则新增接口必然遗漏。
- **不能把权限写死在 JWT 里**：权限变更后旧 token 仍然有效会造成"授了权不生效、收了权仍可用"。
- **不能因为鉴权改造导致现有功能不可用**：存量演示数据必须能继续被访问。
- **不能出现"管理员被锁死"**：超级管理员必须始终可恢复系统。

## 二、授权模型总览

### 2.1 两层授权

平台采用"功能权限 + 数据权限"两层判定，二者是 **AND** 关系：

```
请求 → ① 是否登录？          否 → 401
     → ② 是否拥有该操作的权限码？  否 → 403（无操作权限）
     → ③ 该条数据是否在可见范围内？否 → 403（无数据访问权限）
     → 执行
```

- **第一层（功能权限）**回答"能不能做这件事"：能不能创建 Agent、能不能删除用户、能不能查看审计日志。
- **第二层（数据权限）**回答"能对哪些记录做这件事"：能创建，但只能改自己创建的；能查看列表，但列表里只有自己的和公开的。

两层都必须存在。只有功能权限，等于所有人共享全部数据；只有数据权限，等于谁都能调用删除接口只是删不掉别人的数据，仍然危险。

### 2.2 授权来源

用户的最终权限 = 其所有角色的权限并集 + 数据范围的**最宽值**。

- 一个用户可以有多个角色。
- 多个角色中只要有一个角色具备某权限码，即视为拥有。
- 多个角色中只要有一个角色的数据范围是"全部"，则该用户的数据范围为"全部"。
- `is_superuser = true` 的用户跳过全部两层校验（见 3.5）。

### 2.3 权限判定矩阵

| 角色数据范围 | 资源可见范围 | 资源归属 | 可读 | 可写（改/删/发布） |
|---|---|---|---|---|
| 全部 | 任意 | 任意 | ✅ | ✅ |
| 仅本人 | 公开 | 他人 | ✅ | ❌ |
| 仅本人 | 公开 | 自己 | ✅ | ✅ |
| 仅本人 | 私有 | 自己 | ✅ | ✅ |
| 仅本人 | 私有 | 他人 | ❌ | ❌ |
| 超级管理员 | 任意 | 任意 | ✅ | ✅ |

> "可写"一列的前提是**同时拥有对应的功能权限**。矩阵只描述第二层。

## 三、功能权限需求

### 3.1 权限码规范

- 格式：`模块:动作`，全小写，下划线分隔单词，例如 `agent:create`、`knowledge:document_upload`。
- 模块名与后端路由前缀、前端菜单模块保持一致。
- 动作名使用动词或动词短语：`list`、`read`、`create`、`update`、`delete`、`publish`、`rollback`、`assign_role`、`document_upload` 等。
- 权限码全局唯一（现有 `permissions.code` 已是唯一索引）。
- 创建权限时后端必须校验格式，非法格式拒绝创建。

### 3.2 通配符规则

| 写法 | 含义 | 示例 |
|---|---|---|
| `*` | 全部权限 | 超级管理员角色 |
| `模块:*` | 该模块下全部权限 | `agent:*` 覆盖 `agent:create`、`agent:publish` 等 |
| `模块:动作` | 精确权限 | `agent:read` |

匹配优先级：精确匹配 → 模块通配 → 全局通配。

**约束**：通配符只允许出现在末尾（`*` 或 `模块:*`），不允许 `agent:read*` 这种中间通配，避免规则不可预测。

**兼容性**：现有种子数据中的 `agent:*`、`model:*`、`prompt:*`、`knowledge:*`、`tool:*` 继续有效，但 V2 会把它们拆成细粒度权限码，同时保留模块通配作为"一键授予整个模块"的便捷项。

### 3.4 接口保护范围

#### 必须保护（要求登录 + 功能权限）

除下列白名单外，`/api/v1/**` 下的全部接口一律要求登录并校验权限。

#### 白名单（免登录）

| 接口 | 理由 |
|---|---|
| `GET /health` | 健康检查 |
| `POST /api/v1/auth/login` | 登录入口 |
| `GET /api/v1/captcha` | 登录前需要验证码 |
| `POST /api/v1/captcha` | 验证码校验 |
| `GET /users/me` | 要求登录，但不要求任何权限码（返回自己的身份与权限） |

#### 生产环境要求

- `/docs`、`/redoc`、`/openapi.json` 在生产环境默认关闭，或仅允许超级管理员访问。开发环境保持开启。
- CORS 白名单按部署环境配置，不允许沿用开发环境的 `*` 式宽泛配置。

### 3.5 超级管理员

- `is_superuser = true` 的用户跳过功能权限和数据权限校验。
- `is_superuser` 只能通过数据库或初始化脚本设置，**任何 API 都不得提供修改该字段的入口**（现有 `UserCreate` 已不包含该字段，需保持）。
- 系统必须至少保留一个可用（`is_active = true`）的超级管理员：
  - 禁止删除最后一个超级管理员；
  - 禁止禁用最后一个超级管理员；
  - 禁止把最后一个超级管理员从管理员角色上移除。

### 3.6 鉴权失败的错误码

沿用项目现有的"HTTP 200 + 业务 code"约定，新增以下业务码：

| code | 含义 | 前端行为 |
|---|---|---|
| `40100` | 未登录或 token 已过期 | 清除本地 token，跳转 `/login` |
| `40101` | 账号已被禁用 | 提示后跳转 `/login` |
| `40300` | 缺少操作权限 | 停留当前页，提示"无操作权限" |
| `40301` | 无权访问该数据 | 停留当前页，提示"无权访问该资源" |
| `40302` | 非资源归属人，无法修改 | 提示"只有创建者可修改" |
| `40303` | 越权授权（授予了自己不具备的权限） | 提示具体被拒绝的权限码 |
| `40901` | 角色已被用户引用，无法删除 | 提示关联用户数 |
| `40902` | 权限已被角色引用，无法删除 | 提示关联角色数 |

> 与现有 `BizException` 风格保持一致：HTTP 状态码仍为 200，由 `code` 区分业务结果。

**关于"不可见数据"的返回策略**：V2 采用明确的 `40301`，而不是伪装成 404。理由：内部企业平台优先保证可排查性，用户能明确知道"是权限问题"而不是"数据丢了"。若未来对外暴露 API，再统一切换为 404 防枚举。

## 四、数据权限需求

### 4.1 受控资源

| 资源 | 是否做数据隔离 | 说明 |
|---|---|---|
| Agent | ✅ | 含版本、发布、启停 |
| 知识库 | ✅ | 含文档、分段、检索测试 |
| Prompt | ✅ | 含版本、发布、回滚 |
| 工具 | ✅ | 含启停、测试 |
| 模型 | ❌ | 平台级配置，仅功能权限 |
| 供应商 | ❌ | 平台级配置，仅功能权限 |
| 用户/角色/权限 | ❌ | 管理类数据，仅功能权限 |
| 对话日志 | 未来 | 后端未实现，规则见 4.8 |

### 4.2 新增数据字段

| 表 | 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|---|
| `roles` | `data_scope` | varchar(20) | `self` | `all` / `self` |
| `agents` | `owner_id` | bigint, 可空 | 无 | 关联 `users.id`，创建时写入当前登录用户 |
| `agents` | `visibility` | varchar(20) | `private` | `private` / `public` |
| `knowledge_bases` | `owner_id` | bigint, 可空 | 无 | 同上 |
| `knowledge_bases` | `visibility` | varchar(20) | `private` | 同上 |
| `prompts` | `owner_id` | bigint, 可空 | 无 | 同上 |
| `prompts` | `visibility` | varchar(20) | `private` | 同上 |
| `tools` | `owner_id` | bigint, 可空 | 无 | 同上 |
| `tools` | `visibility` | varchar(20) | `private` | 同上 |

索引要求：每张受控表增加 `owner_id` 普通索引，以及 `(visibility, owner_id)` 联合索引，保证列表过滤性能。

`permissions` 表**不新增字段**：权限所属模块由 `code` 的前缀推导（`agent:create` → 模块 `agent`），避免为展示需求引入冗余字段。

**保留 `created_by` 字段**：继续用于界面展示创建者姓名；`owner_id` 是唯一的权限判定依据。两者不一致时以 `owner_id` 为准。

### 4.3 可见范围语义

| 值 | 含义 | 读 | 写 |
|---|---|---|---|
| `private` | 私有，仅归属人可见 | 仅归属人 + 数据范围为 `all` 的用户 + 超级管理员 | 仅归属人 + 数据范围为 `all` 的用户 + 超级管理员 |
| `public` | 公开，全员可见 | 所有拥有该模块 `*:read` 或 `*:list` 权限的用户 | **仅归属人** + 数据范围为 `all` 的用户 + 超级管理员 |

> `public` 是"可见"而不是"可编辑"。这一条必须在产品文案中明确，避免用户误以为公开就是共享编辑。

### 4.4 数据权限判定规则

**可读**：满足任一即可
1. 用户 `is_superuser = true`；
2. 用户的角色数据范围为 `all`；
3. 资源 `visibility = public`；
4. 资源 `owner_id = 当前用户 id`。

**可写（改 / 删 / 发布 / 启停 / 回滚）**：满足任一即可
1. 用户 `is_superuser = true`；
2. 用户的角色数据范围为 `all`；
3. 资源 `owner_id = 当前用户 id`。

**可改可见范围**：同"可写"。

**收藏/引用类操作**：不单独定义，随所属资源判定。

### 4.5 子资源与继承

以下资源不单独设置归属，**一律继承父资源的可见性**：

| 子资源 | 父资源 |
|---|---|
| Agent 版本、发布记录 | Agent |
| Prompt 版本 | Prompt |
| 知识库文档 | 知识库 |
| 文档分段 | 知识库（经文档） |
| 知识库检索测试结果 | 知识库 |

要求：
- 任何通过子资源 ID 直接访问的接口，必须先解析父资源并校验父资源可见性，不能因为"知道子资源 ID"就绕过。
- 子资源的写操作除父资源可写外，还需具备对应的功能权限（如 `knowledge:segment_update`）。
- 父资源被删除时，子资源按现有级联规则处理。

### 4.6 跨资源引用

Agent 配置会引用模型、知识库、Prompt、工具。规则：

1. **保存时校验**：创建或更新 Agent 时，所引用的每个资源对操作者必须"可读"，否则拒绝保存并指出具体资源。
2. **运行时不再按调用者校验**：Agent 执行时以其配置为准，不再回溯校验最终调用者对这些下游资源的权限。
3. **可见性变更不回扫**：已存在的引用关系不会因下游资源改为 `private` 而失效或报错。
4. **引用已删除资源**：按现有外键/空值策略处理，界面上需提示"引用的资源已不可用"。

> 第 2、3 条是本期明确接受的取舍：Agent 作为平台内的服务主体运行，避免每次调用都做权限回溯带来的性能与行为不确定性。风险与替代方案见 11.3。

### 4.7 存量数据迁移

| 场景 | 迁移规则 |
|---|---|
| `roles` 存量记录 | `admin` → `data_scope = all`；`operator` 及其他 → `self` |
| 业务资源 `owner_id` | 用 `created_by` 的用户名匹配 `users.username`；匹配成功写入对应用户 id |
| 匹配不到归属人 | 统一归属到超级管理员（初始化脚本创建的 `admin`） |
| 业务资源 `visibility` | 存量数据统一置为 `public`，保证升级后现有演示数据仍可被所有已登录用户看到 |
| 新建资源 | 默认 `private`；由创建人在表单中选择是否公开 |
| 权限码 | 保留现有权限码，新增 3.3 中的细粒度权限码；`admin` 角色补齐全部权限，`operator` 角色按 4.9 重新配置 |

**存量权限码与新体系的对应关系**（迁移时必须处理）：

| 现有权限码 | 处理方式 |
|---|---|
| `user:list` / `user:create` / `user:delete` / `role:list` / `permission:list` | 保留 |
| `user:update` | 后端无对应接口，保留记录但标记为废弃，不授予任何角色 |
| `role:assign` | 重命名为 `role:assign_perm`，同步更新 `role_permissions` 关联 |
| `agent:*` / `model:*` / `prompt:*` / `knowledge:*` / `tool:*` | 作为模块通配权限保留，同时补入 3.3 的细粒度权限码 |

权限码重命名必须同步清理相关用户的权限缓存，避免出现"旧码仍生效"的窗口期。

迁移必须可重复执行（幂等），并提供回滚脚本。

### 4.8 未来模块的强制约定

后续新增业务模块（对话日志、统计、API Key 等）时：

- 若资源天然有归属，必须加 `owner_id` + `visibility`，并纳入统一过滤。
- **禁止任何聚合统计直接 `count` 全表**：仪表盘、用量、费用等统计必须按当前用户的数据权限过滤后聚合。
- 对话日志的归属规则待定：候选方案为"归属 Agent 的归属人"或"归属会话发起人"，V2 不实现，但需在实现前明确。

### 4.9 默认角色的权限配置（迁移后）

| 角色 | 数据范围 | 权限集合 |
|---|---|---|
| `admin`（管理员） | `all` | 全部权限（`*`） |
| `operator`（运营人员） | `self` | Agent / Prompt / 知识库 / 工具的全模块权限；模型与供应商仅 `list` + `read`；无用户、角色、权限管理权限 |

> 现状：`operator` 只有 `user:list`、`role:list`、`permission:list` 三个权限，无法进行任何业务操作。V2 必须重新配置，否则该角色在启用鉴权后等同于"只读访客"。

## 五、后端授权实现要求（行为层面）

### 5.1 统一收口

- **功能权限**：必须通过统一的依赖/装饰器声明在路由层，不允许在各 Service 内散落判断。
- **数据权限**：必须在 Repository 的查询构造处统一注入过滤条件，不允许各 API 或 Service 自行拼接 `where`。
- **单条数据校验**：Service 在读写单条记录前调用统一的数据权限判定，判定失败抛出 `40301` / `40302`。
- **分页总数**：`total` 必须与过滤后的结果集一致，禁止出现"列表过滤了但 total 是全表"的情况。

### 5.2 鉴权执行顺序

1. 解析并校验 JWT（失败 → `40100`）；
2. 查询用户，校验存在与启用状态（失败 → `40100` / `40101`）；
3. 判断是否超级管理员（是 → 跳过后续权限判断）；
4. 校验功能权限码（失败 → `40300`）；
5. 解析数据范围（`all` / `self`）；
6. 在查询或单条校验中应用数据权限（失败 → `40301` / `40302`）。

### 5.3 权限集合加载与缓存

**加载方式**：从数据库按 `user_id` 关联 `user_roles → roles → role_permissions → permissions` 得到权限码集合与数据范围。

**缓存要求**：

| 项 | 要求 |
|---|---|
| 缓存介质 | Redis（项目已有 Redis 依赖） |
| 缓存内容 | 权限码集合、数据范围、是否超级管理员 |
| 键设计 | 按用户维度，包含用户 id |
| 有效期 | 5 分钟 |
| 主动失效 | 用户角色变更、角色权限变更、角色删除、权限修改/删除、用户禁用/删除时立即失效 |
| 失效范围 | 角色权限变更时，需失效该角色下所有用户的缓存 |
| Redis 不可用 | 降级为直接查库，保证功能可用，同时记录告警日志 |
| 权限码变更 | 新增/删除权限码后，相关角色用户的缓存必须失效 |

**明确否决的方案**：把权限列表写入 JWT。原因：token 有效期 30 分钟且无法主动吊销，会出现"已收权仍可操作"的安全缺口。

### 5.4 权限数据接口

`GET /users/me` 的响应必须扩展为包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `username` / `email` / `is_active` | 现有字段 | 保持不变 |
| `is_superuser` | boolean | 新增，前端用于整体放行判断 |
| `roles` | 数组 | 新增，每项含 `id`、`code`、`name` |
| `permissions` | 字符串数组 | 新增，已展开的权限码集合（含通配符原样返回） |
| `data_scope` | 字符串 | 新增，`all` / `self`，多角色取最宽 |

要求：
- 该接口只返回当前登录用户自己的信息，不接受用户 id 参数。
- 超级管理员的 `permissions` 可返回 `["*"]`，由前端按通配符处理。

### 5.5 授权变更的审计（P1）

必须记录以下事件：给用户分配/移除角色、给角色分配/移除权限、创建/删除角色、创建/删除权限、修改角色数据范围。

每条记录至少包含：操作人、操作时间、操作类型、目标对象、变更前、变更后、来源 IP。

> 审计表后端尚未实现。V2 将其列为 P1，若本期资源不足，至少保证应用日志中可检索到上述事件。

## 六、前端权限需求

### 6.1 身份与权限获取

- 登录成功后调用 `/users/me` 获取当前用户、角色、权限集合、数据范围、是否超级管理员。
- 权限信息保存在前端全局上下文（React Context），供菜单、路由、按钮统一读取。
- 权限信息**不写入 localStorage 作为长期依据**，每次应用启动重新拉取，避免展示过期权限。
- 收到 `40100` / `40101`：清除 token，跳转 `/login`。
- 收到 `40300` / `40301` / `40302`：不跳转登录页，就地提示，并保留当前页面。

### 6.2 菜单级控制

- 侧边栏每个菜单项声明所需权限码（如"Agent管理"需要 `agent:list`）。
- 无权限的菜单项**不渲染**，而不是置灰。
- 一级分组（如"系统管理"）下所有子项均无权限时，整个分组不渲染。
- 用户登录后默认落在其有权限的第一个菜单；若 `dashboard` 本身无权限要求，则仍落在工作台。

**菜单与权限映射（V2 要求）**：

| 菜单 | 权限码 |
|---|---|
| 工作台 | 无（登录即可） |
| Agent管理 | `agent:list` |
| 模型管理 | `model:list` 或 `provider:list` |
| Prompt管理 | `prompt:list` |
| 知识库管理 | `knowledge:list` |
| 工具管理 | `tool:list` |
| 对话日志 | `conversation:list` |
| 数据统计 | `analytics:usage` 或 `analytics:cost` 或 `analytics:evaluation` |
| 系统管理 → 用户管理 | `user:list` |
| 系统管理 → 角色管理 | `role:list` |
| 系统管理 → 权限管理 | `permission:list` |
| 系统管理 → API Key | `system:apikey_manage` |
| 系统管理 → 审计日志 | `system:audit_read` |
| 系统管理 → 告警规则 | `system:alert_manage` |
| 系统管理 → 系统设置 | `system:settings_manage` |

### 6.3 路由级控制

- 所有受保护路由在 `AuthGuard` 之内再套一层权限守卫，声明所需权限码。
- 无权限时跳转统一的 403 页面，而不是空白页或登录页。
- 403 页面提供"返回工作台"和"返回上一页"两个出口。
- **直接输入 URL 与点击菜单行为必须一致**：都不能绕过。

### 6.4 按钮级控制

列表页与详情页的操作按钮按权限码显隐：

| 页面 | 操作 | 权限码 |
|---|---|---|
| Agent 列表/详情 | 新建 | `agent:create` |
| Agent 列表/详情 | 编辑 | `agent:update` + 数据可写 |
| Agent 列表/详情 | 删除 | `agent:delete` + 数据可写 |
| Agent 详情 | 发布/回滚/启停 | `agent:publish` / `agent:rollback` / `agent:start` / `agent:stop` |
| Prompt | 新建/编辑/删除/发布/回滚 | 对应 `prompt:*` |
| 知识库 | 新建/编辑/删除 | `knowledge:create` / `knowledge:update` / `knowledge:delete` |
| 知识库文档 | 上传/删除/重试 | `knowledge:document_*` |
| 知识库分段 | 编辑/删除 | `knowledge:segment_*` |
| 工具 | 新建/编辑/删除/启停/测试 | 对应 `tool:*` |
| 模型/供应商 | 新建/编辑/删除/测试 | 对应 `model:*` / `provider:*` |
| 用户管理 | 新建/删除/分配角色 | `user:create` / `user:delete` / `user:assign_role` |
| 角色管理 | 新建/编辑/删除/分配权限 | 对应 `role:*` / `role:assign_perm` |
| 权限管理 | 新建/编辑/删除 | 对应 `permission:*` |

**数据级按钮控制**：即使拥有 `agent:update`，若当前记录不可写（非归属人且数据范围为 `self`），编辑与删除按钮也必须隐藏或禁用，并提示"仅创建者可修改"。

### 6.5 数据权限的前端呈现

- 列表页展示"创建人"与"可见范围"（公开/私有）标识。
- 创建/编辑表单增加"可见范围"选择项，默认"私有"。
- 仅归属人或数据范围 `all` 的用户可以修改可见范围；无权限时该项只读。
- 无任何数据可见时，展示空状态文案："暂无可访问的数据"，并区分"确实没有数据"与"没有权限"。
- 前端不得自行做数据过滤后假装是服务端结果；列表数据以服务端返回为准。

### 6.6 角色管理页面增强

- 角色表单增加"数据范围"选项：全部数据 / 仅本人数据，默认"仅本人数据"。
- 角色列表展示数据范围列。
- 分配权限时按模块分组展示权限码，支持"全选模块"（等价于授予 `模块:*`）。
- 不可将 `admin` 角色的数据范围改为 `self`（系统角色保护）。

### 6.7 权限管理页面增强

- 权限列表按模块前缀分组，展示中文模块名。
- 创建权限时提供模块与动作的格式提示，前端做基础校验，后端做最终校验。
- 删除被引用的权限时，展示后端返回的关联角色数量。
- 权限码一经创建不可修改（现有实现已限制），如需变更应新建并迁移。

### 6.8 前端权限判断工具要求

- 提供统一的权限判断方法，支持精确码与通配符匹配，规则必须与后端一致（精确 → 模块通配 → 全局通配）。
- 提供声明式组件用于包裹需要权限的 UI 片段。
- 提供 Hook 用于在逻辑中判断权限。
- 禁止在页面中散落字符串比较（如直接判断 `permissions.includes('agent:create')`），必须走统一方法，保证通配符规则一致。

## 七、授权管理流程与安全约束

### 7.1 谁能授权

- 给用户分配角色：需要 `user:assign_role`。
- 给角色分配权限：需要 `role:assign_perm`。
- 创建/删除角色：需要 `role:create` / `role:delete`。
- 创建/删除权限：需要 `permission:create` / `permission:delete`。
- 超级管理员不受限制。

### 7.2 防提权（必须实现）

1. **不能授予自己没有的权限**：分配角色权限时，所选的每个权限码都必须是操作者自身权限集合的子集（通配符按展开后判断），否则整体拒绝并返回 `40303`，指出越权的权限码。
2. **不能分配权限超出自己的角色**：给用户分配角色时，目标角色的权限集合必须是操作者权限集合的子集。
3. **不能修改自己的角色**：用户不得通过 `PUT /users/{id}/roles` 修改自己的角色，防止自提权；超级管理员除外。
4. **不能修改超级管理员**：非超级管理员不得修改超级管理员的角色、状态或删除该账号。

### 7.3 角色与权限的删除约束

| 操作 | 约束 |
|---|---|
| 删除角色 | 系统内置角色（`admin`）不可删除；仍有用户关联时拒绝删除（`40901`） |
| 修改 `admin` 角色 | 不允许删除其权限、不允许改名为其他 code、不允许改数据范围 |
| 删除权限 | 仍被角色引用时拒绝删除（`40902`） |
| 删除用户 | 若该用户拥有业务资源，删除前需二次确认，并将其资源归属转移给超级管理员，避免产生无主数据 |

### 7.4 授权生效时延

- 主动失效后：下一次请求立即生效。
- 缓存未失效的极端情况（如 Redis 故障恢复后残留）：最长 5 分钟生效。
- 前端在自己被调整权限后，需重新拉取 `/users/me` 刷新界面。

### 7.5 初始化与幂等

- 初始化脚本必须可重复执行，不产生重复角色、权限、关联记录。
- 初始化后保证：存在一个可用的超级管理员；`admin` 角色拥有全部权限且数据范围为 `all`；`operator` 角色按 4.9 配置。

## 八、验收标准

### 8.1 功能权限

| 编号 | 场景 | 预期结果 |
|---|---|---|
| A-01 | 未登录访问 `GET /agents` | 返回 `40100`，前端跳转登录页 |
| A-02 | 只有 `agent:list` 的用户访问 `POST /agents` | 返回 `40300` |
| A-03 | 拥有 `agent:*` 的用户访问 `POST /agents` | 成功 |
| A-04 | 拥有 `agent:create` 的用户访问 `DELETE /agents/{id}` | 返回 `40300` |
| A-05 | 只有 `user:list` 的用户访问 `GET /roles` | 返回 `40300` |
| A-06 | 超级管理员访问任意接口 | 全部成功（白名单逻辑除外） |
| A-07 | 角色权限被移除后，用户下一次请求 | 立即被拒绝（缓存已失效） |
| A-08 | 用户被禁用后再次请求 | 返回 `40101` |
| A-09 | 新增接口未声明权限码 | 评审不通过；测试用例覆盖"未声明即拒绝"的清单检查 |
| A-10 | Redis 服务不可用 | 鉴权仍能工作（降级查库），日志有告警 |

### 8.2 数据权限

| 编号 | 场景 | 预期结果 |
|---|---|---|
| B-01 | 数据范围 `self` 的用户查询 Agent 列表 | 只返回自己创建的 + 公开的 |
| B-02 | 用户直接访问他人私有 Agent 详情 | 返回 `40301` |
| B-03 | 用户编辑他人公开 Agent | 返回 `40302` |
| B-04 | 用户删除自己创建的 Agent | 成功 |

## 十一、待确认决策与默认假设

以下条目是本文在缺少进一步输入时采用的默认判断。若与你的预期不符，请在评审时指出，我会同步修订本文。

### 11.1 已采用默认假设

| 编号 | 问题 | 默认决策 | 理由 |
|---|---|---|---|
| Q1 | 是否按部门隔离数据 | 本期不做，角色数据范围只有 `all` / `self` | 数据库无部门字段，补组织架构属于独立工程 |
| Q2 | 公开资源能否被他人编辑 | 不能，公开仅代表可读 | 避免"公开即共享编辑"造成误删 |
| Q3 | 不可见数据返回 403 还是 404 | 403 + 明确文案 | 内部平台优先可排查性 |
| Q4 | Agent 运行时是否按调用者校验下游资源 | 不校验，仅保存时校验引用 | 避免运行期权限回溯的复杂性与性能开销 |
| Q5 | 模型/供应商是否做数据隔离 | 不做 | 平台级配置，隔离后无法共享 |
| Q6 | 权限缓存时长 | 5 分钟 + 主动失效 | 平衡性能与一致性 |
| Q7 | `created_by` 是否废弃 | 保留用于展示，新增 `owner_id` 作为判定依据 | 减少迁移风险 |
| Q8 | 存量数据可见范围 | 统一 `public` | 保证升级后演示数据仍可见 |
| Q9 | 是否引入团队概念 | 本期不做 | 与 Q1 同源 |
| Q10 | 审计日志是否本期 | 列为 P1 | 不阻塞授权主流程 |

### 11.2 必须由你确认的问题

1. **业务资源默认可见范围**：新建资源默认 `private` 是否符合你们的协作习惯？若团队更希望默认共享，可改为默认 `public`。
2. **`operator` 角色的最终权限集合**：本文按"业务全权、系统只读"配置，是否符合预期？
3. **是否需要"只读访客"角色**：若需要，V2 需新增内置角色 `viewer`（数据范围 `self`，仅 `*:list` / `*:read`）。
4. **用户删除后的资源归属**：本文采用"转移给超级管理员"，是否需要改为"禁止删除有资源的用户"？

### 11.3 已知风险与接受说明

| 风险 | 说明 | 缓解 |
|---|---|---|
| 新增接口漏声明权限 | 开发者忘记加权限依赖会导致接口裸露 | 在评审清单与测试中强制检查；逐步引入"未声明即拒绝"的兜底机制 |
| 通配符过度授权 | `*` 或 `模块:*` 会放大权限 | 仅超级管理员与 `admin` 角色允许 `*`；分配界面默认展示细粒度权限 |
| 缓存与数据库短暂不一致 | 主动失效失败时最长 5 分钟延迟 | TTL 兜底 + 告警 |
| 跨资源引用泄露 | Agent 可能间接访问调用者不可见的资源 | 保存时校验 + 在 UI 上提示引用风险 |
| 归属人为空 | 迁移匹配失败或系统创建的资源 | 统一归属超级管理员，并在列表中标识 |
| 最后一任管理员丢失 | 误操作导致无人可管理 | 超级管理员数量下限校验 |

## 十二、术语表

| 术语 | 含义 |
|---|---|
| 功能权限 | 能否执行某个操作，由权限码控制 |
| 数据权限 | 能对哪些数据执行已获授权的操作 |
| 权限码 | `模块:动作` 形式的字符串标识 |
| 数据范围 | 角色属性，`all`（全部数据）或 `self`（仅本人数据） |
| 可见范围 | 资源属性，`private`（仅归属人）或 `public`（全员可读） |
| 归属人 | 资源的创建者，由 `owner_id` 标识 |
| 越权授权 | 授予他人自己都不具备的权限 |
| 超级管理员 | `is_superuser = true` 的用户，跳过全部权限校验 |
